
# Шаг 1: Почему словари — это плохо. Знакомство с Pydantic.

До этого момента мы передавали данные поштучно: id, name, limit. Но что, если нам нужно отправить на сервер целую карточку товара или профиль пользователя с десятком полей?

В классическом Python для этого используют словари (dict).

```python
# Обычный словарь
task = {
    "name": "Купить еду",
    "priority": 1,
    "is_done": False
}
```
### В чем проблема словарей?

Для маленьких скриптов словари подходят идеально. Но для API, которым пользуются другие люди, **словари — это источник проблем**.

1. **Нет проверки типов:**  
    Вы можете написать "priority": "высокий" (текст), хотя ваша программа ожидает число. Python не выдаст ошибку сразу, всё сломается позже, глубоко внутри логики.
    
2. **Опечатки в ключах:**  
    Если вы напишете task["nmae"] (опечатка), программа упадет с ошибкой KeyError. Редактор кода (IDE) не подскажет вам, что вы ошиблись, потому что он не знает, какие ключи должны быть в словаре.
    
3. **Неизвестность:**  
    Глядя на функцию def create_task(task: dict), разработчик понятия не имеет, что должно лежать внутри этого dict. Ему нужно лезть в документацию или читать весь код функции.
    

### Решение: Pydantic

**Pydantic** — это библиотека, которая идет в комплекте с FastAPI. Она заставляет данные подчиняться правилам.  
Вместо хаотичных словарей мы будем описывать **Схемы (Models)**.

### Класс BaseModel

Основа всего — класс BaseModel. Чтобы описать структуру данных, вы создаете класс, который наследуется от него.

```python
from pydantic import BaseModel

class STask(BaseModel):
    name: str
    description: str
    is_done: bool
    priority: int
```
**Примечание по неймингу:**  
В сообществе FastAPI принято называть Pydantic-модели **Схемами**.  
Чтобы не путать их с моделями базы данных (которые будут позже), многие разработчики добавляют префикс S (Schema) или суффикс Schema. Например: STask или TaskSchema.

### Что нам это дает?

Как только вы описали класс STask, происходит магия:

1. **Гарантия типов:** Если вы попробуете положить текст в поле priority (которое int), Pydantic попытается его сконвертировать. Если не выйдет — он выдаст понятную ошибку (ту самую 422).
    
2. **Помощь IDE:** Теперь, когда вы поставите точку (task.), редактор покажет выпадающий список полей: name, description и т.д. Опечататься невозможно.
    
3. **Валидация JSON:** FastAPI использует этот класс, чтобы автоматически проверять входящие JSON-запросы от клиентов.


# Шаг 2: Объявление полей и их типов

Мы создали класс-наследник BaseModel. Теперь нужно наполнить его содержимым.  
В Pydantic поля объявляются так же, как переменные с аннотацией типов в Python.

Синтаксис:  
имя_поля: Тип = Значение_по_умолчанию

### 1. Обязательные поля

Если вы укажете только тип, поле считается **обязательным**.  
Клиент **обязан** передать его в JSON. Если он этого не сделает — получит ошибку.

```python 
class STaskAdd(BaseModel):
 name: str # Обязательно (строка) 
 priority: int # Обязательно (число)
```

### 2. Поля со значением по умолчанию

Часто мы хотим, чтобы поле было необязательным для клиента. Если клиент его не прислал, мы используем какое-то стандартное значение.

```python
class STaskAdd(BaseModel):
    name: str
    is_done: bool = False  # Если не прислали, будет False
```
Теперь клиент может прислать такой JSON: {"name": "Дело"}.  
Pydantic сам добавит в ваш объект поле is_done, равное False.

### 3. Необязательные поля (Nullable)

Что делать, если значения по умолчанию нет? Например, у задачи может быть "Описание", а может и не быть. В базе данных это называется NULL.

В Python мы используем None.  
Синтаксис: Тип | None = None.
```python
class STaskAdd(BaseModel):
    name: str
    description: str | None = None
```

- Если клиент пришлет {"description": "Текст"}, в переменной будет строка.
    
- Если клиент ничего не пришлет (или пришлет null), в переменной будет None.
    

> **Обратите внимание:** Если вы напишете просто description: str | None (без = None), поле останется **обязательным**, просто клиент сможет прислать туда null явно. Чтобы поле стало необязательным, всегда добавляйте = ... в конце.

### 4. Списки (Lists)

Pydantic отлично работает со сложными структурами. Например, у задачи может быть список тегов.
```python
class STaskAdd(BaseModel):
    name: str
    tags: list[str] = [] # Список строк, по умолчанию пустой
```
Pydantic проверит, что:

1. Это именно список (массив []).
    
2. Каждый элемент внутри списка — это строка.  
    Если клиент пришлет ["work", 123], Pydantic попытается превратить число 123 в строку "123".
    

### Собираем всё вместе

Давайте напишем полную схему для создания задачи, которую мы будем использовать в проекте.

Добавьте в новый файл schemas.py (создайте его рядом с main.py):
```python
from pydantic import BaseModel

class STaskAdd(BaseModel):
    name: str
    description: str | None = None
    is_done: bool = False
```
**Как это читается:**  
"Я ожидаю объект, у которого точно есть name (строка). Возможно, есть description (строка), но если нет — пусть будет None. И возможно есть is_done (булево), если нет — считаем False".


# Шаг 3: Тонкая настройка полей (Класс Field)

Мы научились указывать типы: "Имя — это строка". Но строка бывает разной.

- Пустая строка "" — это тоже строка.
    
- Строка длиной в 10 000 символов ("Война и мир") — это тоже строка.
    

Скорее всего, ваша база данных или логика не готовы принять задачу с пустым именем или приоритет -500.  
Для добавления ограничений (валидации) и улучшенного описания используется функция **Field**.

### Импорт

Для начала её нужно импортировать:
```python
from pydantic import BaseModel, Field
```
### 1. Валидация данных (Ограничения)

Field используется вместо обычного значения по умолчанию. Внутри него мы пишем правила.

#### Для строк:

- min_length: Минимальная длина.
    
- max_length: Максимальная длина.
```python
class STaskAdd(BaseModel):
    # Имя не может быть короче 2 символов и длиннее 100
    name: str = Field(min_length=2, max_length=100)
```

#### Для чисел:

- gt (greater than): Больше чем (>).
    
- ge (greater or equal): Больше или равно (>=).
    
- lt (less than): Меньше чем (<).
    
- le (less or equal): Меньше или равно (<=).

```python
class STaskAdd(BaseModel):
    name: str
    # Приоритет от 1 до 10
    priority: int = Field(ge=1, le=10)
```

### 2. Документация (Описание)

Помните Swagger UI? Field позволяет добавить туда человеческие описания. Это очень полезно для фронтенд-разработчиков, которые будут читать вашу документацию.

- description: Текстовое описание поля (поддерживает Markdown).
    
- title: Красивое название поля.
    
- examples: Пример данных (чтобы кнопка "Try it out" сразу подставляла красивые значения).

```python
description: str | None = Field(
    default=None, 
    title="Детали задачи",
    description="Здесь можно добавить **подробное** описание до 1000 знаков"
)
```

### 3. Проблема обязательных полей с Field

Внимательный студент спросит: "Если я пишу = Field(...), это значит, что у поля есть значение по умолчанию? Оно становится необязательным?"

Это тонкий момент.  
Если вы просто напишете name: str = Field(min_length=2), Pydantic может посчитать, что значение по умолчанию — это сам объект Field (хотя в новых версиях это поправили, лучше быть явным).

Чтобы сказать: **"Поле ОБЯЗАТЕЛЬНОЕ, но у него есть правила валидации"**, используется специальный объект — **Многоточие (...)**.
```python
class STaskAdd(BaseModel):
    # Обязательное поле с валидацией
    name: str = Field(..., min_length=2) 
    
    # Необязательное поле (значение по умолчанию None)
    description: str | None = Field(None, max_length=500)
```
